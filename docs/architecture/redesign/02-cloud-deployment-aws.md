# Makthab v3 — Phase 2: AWS Cloud Deployment

**Status:** Implementation in progress — Terraform modules, CI/CD, storage
adapter, and runbook landed under `infra/terraform/`, `.github/workflows/`,
`server/src/lib/storage/`, and `docs/deployment/AWS_RUNBOOK.md`. Apply to a
real AWS account is still a manual `terraform apply` step.
**Depends on:** [01-multi-database-support.md](./01-multi-database-support.md) (Phase 1) — this doc assumes the API talks to PostgreSQL via the DB abstraction landed there, not SQLite.
**See also:** [00-overview-and-prioritization.md](./00-overview-and-prioritization.md) for the overall attack order and phase table.

---

## 1. Executive summary

This doc describes deploying the **current, single-tenant** Makthab app —
one Express/Prisma API, one React/Vite SPA, one organization's data — to
AWS as a repeatable, IaC-defined environment. The guiding constraint is
scale: this app serves one Madrasa's staff (Admin/Accountant/Teacher roles,
realistically single-digit to low-double-digit concurrent users, bursty
around fee-collection and report-generation periods). Every service choice
below is sized for that reality, not for a hyperscale SaaS — the goal is a
deployment a small team can run without a dedicated ops function, at a
monthly cost in the tens of dollars, not thousands.

Where a later multi-tenant phase ([04](./04-multi-tenant-architecture.md))
would force a different choice, this doc flags it explicitly rather than
silently designing for multi-tenancy now. Building single-tenant-right first
keeps this phase small and shippable on its own.

## 2. Architecture & design decisions

### 2.1 Compute: ECS Fargate (chosen) vs. alternatives

| Option | Verdict | Why |
|---|---|---|
| **ECS Fargate** | **Chosen** | No servers to patch, scales to zero-ish (min 1 task), pay-per-task, plays well with a single Docker image built by existing CI. Right complexity level for a small team. |
| Elastic Beanstalk | Rejected | Simpler to start, but its abstraction fights you the moment you need VPC/Secrets Manager/ALB customization — those are exactly the things this app needs. Not meaningfully less ops work than Fargate once configured properly. |
| App Runner | Considered, close second | Even less config than Fargate, built-in HTTPS/scaling. Rejected only because VPC connectivity to RDS requires a VPC connector with its own cost/complexity, and Fargate gives more room to grow into Phase 4 without a re-platform. Revisit if the team wants max simplicity for the single-tenant MVP and is willing to migrate later. |
| Raw EC2 | Rejected | Patching/AMI management is pure ops overhead this team doesn't need to take on. |

Run the API as **one ECS Fargate service, 1-2 tasks** behind an Application
Load Balancer. No separate worker/queue tier — the current app is
synchronous request/response (PDF/Excel generation happens inline in the
request), which is fine at this scale; revisit only if report generation
starts timing out ALB's default 60s idle timeout under real load.

### 2.2 Client hosting: S3 + CloudFront

The Vite production build (`npm run build` in `client/`) is static
HTML/JS/CSS. Serve it from an **S3 bucket with CloudFront** in front (not
served by the Express app) — cheaper, faster (edge caching), and decouples
client deploys from API deploys. CloudFront also terminates TLS for the
client domain via ACM.

**Trade-off accepted:** this means CORS must be configured on the API for
the CloudFront domain (already a pattern in this app — dev CORS already
allows `localhost:5173` per `BUILD_CONTRACT.md` §3). Not a new problem, just
a new origin to allow.

### 2.3 File storage: S3 (replaces `data/files/`)

Today, PDFs (receipts, payslips, reports), Excel exports, and photos are
written to local disk under `data/files/{receipts,payslips,reports,photos}`.
On Fargate, local disk is ephemeral and **not shared across tasks or
across deploys** — this breaks the moment there's more than one task or a
task restarts. **This is a hard blocker for Fargate, not an optional
improvement.**

**Design decision:** replace local `fs.writeFile` calls in `server/src/lib/pdf.ts`
and the report/receipt generation code with writes to an S3 bucket
(`makthab-files-<env>`), keeping the same logical path structure as prefixes
(`receipts/...`, `payslips/...`, `reports/...`, `photos/...`). Serve files
back to the client via short-lived **S3 presigned URLs** generated by the
API, rather than proxying file bytes through Express.

**Dependency flagged for Phase 2 planning:** this requires an actual code
change in `server/`, not just infra — budget it explicitly in the migration
plan below (§9) rather than assuming it's "just infra."

### 2.4 Networking: VPC

- One VPC, 2 AZs (minimum for RDS Multi-AZ / ALB requirements), public +
  private subnets per AZ.
- **Public subnets:** ALB only.
- **Private subnets:** ECS Fargate tasks, RDS instance. No direct internet
  route; outbound internet (for npm/OS updates inside the container image —
  built at CI time, so runtime egress need is minimal) via a NAT Gateway
  **or**, to cut cost at this scale, VPC endpoints for S3/ECR/Secrets
  Manager/CloudWatch Logs instead of a NAT Gateway (NAT Gateway alone runs
  ~$32/mo + data processing; gateway VPC endpoint for S3 is free, interface
  endpoints for ECR/Secrets Manager/Logs are a few dollars each — cheaper
  than NAT for this app's traffic pattern since it needs almost no general
  internet egress at runtime).
- **Security groups:** ALB SG allows 443 from `0.0.0.0/0`; ECS task SG
  allows inbound only from ALB SG on port 3000; RDS SG allows inbound only
  from ECS task SG on port 5432. No security group allows direct internet
  ingress to compute or database.

### 2.5 Database hosting: RDS PostgreSQL, Single-AZ (chosen) vs. Multi-AZ

| Option | Monthly cost delta | Verdict |
|---|---|---|
| Single-AZ `db.t4g.micro` | baseline (~$13-15/mo instance) | **Chosen for MVP/staging and even initial prod** — RDS automated backups + PITR (§8) give an acceptable recovery story at this scale; a few minutes of downtime during an AZ failure is tolerable for a single Madrasa's admin staff, not for a live customer-facing checkout system. |
| Multi-AZ `db.t4g.micro` | +~100% (~$26-30/mo) | Revisit once this is revenue-bearing (i.e., alongside Phase 4 multi-tenancy) — the cost of downtime changes once there are paying tenant customers depending on uptime SLAs. |

Use RDS **PostgreSQL 16**, matching whatever version Phase 1's Prisma
schema targets. Enable automated backups (7-day retention to start) and
storage autoscaling (start at 20GB — this app's data volume, per the
migration doc's 69 students / 672 fees baseline, is trivially small).

**Flag for Phase 4:** a multi-tenant design may move to one RDS instance
with per-tenant Postgres **schemas** (see [04](./04-multi-tenant-architecture.md)
§2) rather than one database per tenant — if so, this same RDS instance
can likely absorb early tenants without immediately needing a bigger
instance class; re-evaluate instance sizing at that point, not now.

### 2.6 Secrets: Secrets Manager

`DATABASE_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET` move out of `.env` files
into **AWS Secrets Manager**, injected into the ECS task as environment
variables via the task definition's `secrets` block (resolved at task
start, never baked into the container image or written to CloudWatch Logs).
Rotation: manual rotation acceptable for MVP; automated rotation is a
Phase 3 security-hardening item, not required to ship Phase 2.

### 2.7 DNS/TLS

Route53 hosted zone for the domain; ACM certificates (one for the
CloudFront client distribution, one for the ALB's API domain, e.g.
`api.makthab.example`) — both free, auto-renewing. No third-party
cert/DNS vendor needed.

## 3. Reference cloud architecture (textual diagram)

```
Browser
  │  HTTPS (client domain)
  ▼
Route53 ──▶ CloudFront (client dist., ACM cert) ──▶ S3 bucket (Vite build, static)
  │
  │  HTTPS (api.* domain), XHR/fetch calls from the SPA
  ▼
Route53 ──▶ ALB (public subnets, ACM cert)
              │  HTTP :3000, private subnets only
              ▼
         ECS Fargate service (1-2 tasks, Express/Prisma API image from ECR)
              │                              │
              │ 5432, private                │ HTTPS, via S3/Secrets Manager
              ▼                              ▼
         RDS PostgreSQL                 S3 (files: receipts/payslips/
         (Single-AZ, private subnet)    reports/photos) + Secrets Manager
                                         (DATABASE_URL, JWT secrets)

Supporting, cross-cutting:
  CI (GitHub Actions) ──▶ ECR (Docker image) ──▶ ECS deploy
  ECS/RDS/ALB ──▶ CloudWatch Logs & Metrics ──▶ Alarms ──▶ SNS (email/Slack)
```

## 5. CI/CD deployment pipeline plan

**IaC choice: Terraform (chosen) over AWS CDK.** Terraform's HCL is
provider-agnostic (matters less here since this is AWS-only, but the state
model and plan/apply workflow is easier for a small team to reason about
and review in PRs than CDK's imperative TS, and it doesn't require the team
to context-switch into "TS that isn't quite the app's TS" — CDK constructs
have their own learning curve separate from application code). Either is
defensible; Terraform is the more common default for teams without prior
AWS CDK experience.

**Pipeline (GitHub Actions), reusing existing scripts:**

1. **On every PR:** `npm install` → `npm run build:shared` → `npm run typecheck`
   → `npm run test -w server` (against an ephemeral SQLite test DB, exactly
   as today — no need to spin up Postgres in CI for this stage; Phase 1's
   testing plan covers cross-DB CI separately).
2. **On merge to `main`:**
   a. Build Docker image for `server/` (new `Dockerfile` needed — multi-stage:
      build shared+server, then a slim `node:20-alpine` runtime layer).
   b. Push image to ECR, tagged with the commit SHA.
   c. Build client (`npm run build -w client`), sync output to the S3 client
      bucket, invalidate the relevant CloudFront paths.
   d. Terraform plan/apply (or `aws ecs update-service --force-new-deployment`
      for a simpler MVP pipeline that just bumps the task definition's image
      tag) to roll the new API image out to ECS.
3. **Manual approval gate** on production deploys (GitHub Actions
   environment protection rule) — cheap insurance for a small team without
   a full staging→canary pipeline yet.

No blue/green or canary deployment infrastructure in this phase — ECS's
built-in rolling deployment (min healthy 100%, max 200%, i.e. spin up new
task, health-check, then drain old) is sufficient at 1-2 task scale.

## 6. Cost optimization

**Rough monthly estimate, single-tenant, us-east-1, right-sized:**

| Item | Est. monthly cost |
|---|---|
| ECS Fargate, 1 task, 0.25 vCPU / 0.5GB, ~730 hrs | ~$9 |
| ALB | ~$16 (base) + trivial LCU cost at this traffic |
| RDS `db.t4g.micro` Single-AZ, 20GB gp3 | ~$13-15 |
| S3 (files bucket + client bucket), low volume | ~$1-3 |
| CloudFront, low traffic | ~$1-2 |
| VPC endpoints (S3 gw free; ECR/Secrets/Logs interface endpoints) | ~$8-10 |
| Secrets Manager (3 secrets) | ~$1.20 |
| Route53 hosted zone | ~$0.50 |
| CloudWatch Logs/Metrics/Alarms, low volume | ~$2-5 |
| **Total** | **~$50-65/mo** |

This excludes ACM (free) and excludes a NAT Gateway (avoided via VPC
endpoints, see §2.4 — the single biggest lever here: skipping NAT saves
~$35-40/mo for an app that needs almost no general internet egress at
runtime).

**Further optimization levers:**
1. **Fargate Spot** for any non-prod (staging) environment — up to ~70%
   compute discount, acceptable since staging can tolerate interruption.
2. **S3 lifecycle rules**: transition report/receipt PDFs older than, say,
   90 days to S3 Glacier Instant Retrieval — financial records likely need
   long retention but are rarely re-accessed after a few months.
3. **RDS start/stop for non-prod**: stop the staging RDS instance outside
   business hours (RDS supports stop for up to 7 days at a time, needs a
   small Lambda/EventBridge scheduler to restart) — meaningful saving if
   staging isn't used 24/7.

## 7. Observability

Keep it minimal and targeted — this is not a system that needs a full
observability platform yet.

- **CloudWatch Logs:** ECS task stdout/stderr (structured JSON logging
  recommended as a small code change, not required to ship) shipped
  automatically via the `awslogs` driver in the task definition.
- **CloudWatch Metrics/Alarms** — alarm on only what actually predicts user
  pain at this scale:
  - ALB 5xx rate > threshold over 5 min → SNS → email/Slack.
  - ECS service running task count < desired count for > 5 min (task
    crash-looping).
  - RDS `FreeStorageSpace` below a floor, and RDS CPU > 80% sustained.
  - RDS `DatabaseConnections` approaching the instance's max connection
    limit (early warning before Phase 1's pooling strategy is exhausted).
- **Explicitly skip for this phase:** distributed tracing (X-Ray), custom
  business metrics dashboards, log aggregation beyond CloudWatch Logs
  Insights — add these only if/when Phase 4 multi-tenancy raises the
  operational stakes enough to justify the setup cost.

## 8. DR / backup strategy

| Target | Value | Justification |
|---|---|---|
| **RPO (data loss tolerance)** | 24 hours (automated daily snapshot) with PITR available down to ~5 min via transaction logs | RDS automated backups give PITR essentially for free within the retention window — use it, don't just rely on daily snapshots. |
| **RTO (recovery time)** | 4 hours | Single-AZ RDS restore-from-snapshot to a new instance is a documented, testable runbook, not automatic failover — 4 hours is realistic for a small team to execute manually, and acceptable for an internal madrasa-admin tool (not a 24/7 customer-facing system) at single-tenant scale. |
| **File storage (S3)** | Versioning enabled, no cross-region replication | Local risk (accidental overwrite/delete) is covered by versioning; regional AWS outage risk is accepted at this scale/cost tier — revisit if/when Phase 4 makes this revenue-critical. |

**Backup runbook (to be written, not just designed) should cover:**
restoring RDS from the latest automated snapshot or a PITR timestamp into a
new instance, repointing the ECS task's `DATABASE_URL` secret at it, and a
smoke-test checklist (reuse `BUILD_CONTRACT.md` §7's Definition-of-Done
flow: login → view a student → collect a fee → generate a report) to
confirm the restore is good before declaring recovery complete.

## 10. Risk assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| S3 migration for files (M3) underestimated — touches PDF/Excel/photo code paths in several routes | Medium | Medium | Budget it as explicit application work (already done above, not folded into "infra"); write it behind a storage-adapter interface so local-disk dev mode still works without AWS creds. |
| Team unfamiliar with Terraform/ECS causes schedule slip | Medium | Medium | Start with a minimal hand-written Terraform module (VPC, RDS, ECS, ALB) rather than a generic module registry pull — easier to understand and debug for a first AWS deployment. |
| Cost overrun from an idle NAT Gateway or oversized RDS left running in a forgotten staging env | Low | Low-Med | Tag all resources by environment, set up AWS Budgets alert at a $ threshold (e.g. $100/mo) from day one. |
| Single-AZ RDS outage causes real downtime | Low | Medium | Accepted trade-off per §2.5; documented restore runbook (§8) keeps RTO bounded; revisit Multi-AZ once revenue-bearing. |
| Secrets accidentally logged (e.g. DATABASE_URL in an error stack trace shipped to CloudWatch) | Low | High | Explicit code review item; defer full remediation detail to [03-security.md](./03-security.md), but flag here since it's a deployment-time exposure vector. |

## 11. Testing/validation plan

Before cutover, validate the deployed environment end-to-end, mirroring the
existing Definition-of-Done checklist in `BUILD_CONTRACT.md` §7:

1. `/health` endpoint returns OK through the ALB and through CloudFront-routed
   API calls (confirm CORS + routing end-to-end, not just container health).
2. Full smoke flow against the deployed stack: login → admit a student →
   collect a fee (confirm the receipt PDF lands in S3 and is retrievable via
   presigned URL, not just that the DB write succeeded) → mark attendance →
   add an expense → run each report type (PDF + Excel) → confirm each
   generated file is in the correct S3 prefix.
3. For the first production environment specifically: this isn't a
   production-*shaped* dry run, it's the actual go-live dataset (M7.5) — the
   real Masjid's student/fee/attendance history, ultimately sourced from
   `docs/source-data/Maktab Detailed - Report.xlsx`. Re-run the same smoke
   flow against it to catch anything that only breaks with realistic data
   volume, and confirm record counts reconcile against the xlsx before
   treating the environment as ready for cutover — a mismatch here is a
   go-live blocker, not a follow-up ticket.
4. Kill an ECS task manually mid-deployment and confirm the ALB removes it
   from rotation and a replacement becomes healthy — validates the rolling
   deployment story before relying on it in production.
5. Dry-run the backup restore runbook (§8) against a snapshot in a scratch
   RDS instance, end-to-end, before go-live — a DR plan that's never been
   executed once is not a plan.
